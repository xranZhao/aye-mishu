## 1. 产品一句话定义

“未尽”是一款面向单个用户的移动端 PWA AI 秘书：接住用户用语音输入法转成的混乱文字，通过多轮对话理解事项、项目、估时、依赖和现实限制，在可靠容量内生成周一至周日计划；所有计划和变更都必须由用户确认后才生效。

它不是普通待办清单，不是小时级日历，也不是自动替用户做业务拆解的 Agent。

## 2. 用户问题与产品目标

### 2.1 用户现状

- 同时维护主业、副业、自媒体、家庭财务、理财和生活关系等多个方向。
- 经常在周日或周一集中说出下一周事项，周中还会不断加入新事情。
- 输入通常来自语音转文字，包含铺垫、口头连接词、纠正和不完整表达。
- 心理上很会 push 自己，容易承诺过多；现实完成率不足后，大量精力消耗在焦虑上。
- 不想自己计算容量、依赖、每天放什么，也不想维护复杂日历。
- 需要秘书直接指出计划不可信，并给出具体的最小调整方案。

### 2.2 产品要解决的核心问题

1. 把混乱原话理解为真实事项，不按标点机械拆分。
2. 把每件工作放回长期核心项目，避免形成一堆孤立任务。
3. 判断事项之间的硬依赖、外部条件和建议顺序。
4. 用真实估时、计时和可靠容量生成本周计划。
5. 周中插入新任务时，明确说出应该替换或延后什么。
6. 让用户每天只面对 1–3 件最值得做的事。
7. 用真实计时和周报帮助用户校准对自己的认识，减少虚假承诺和焦虑。

## 3. 秘书人格与决策边界

秘书必须：

- 冷静、明确、直接，但不攻击用户。
- 先给推荐结论，再给事实理由。
- 可以明确说“这些事情本周放不下”。
- 超容量时必须点名保留什么、移出什么，不能只问“你想调整哪个”。
- 鼓励基于事实，例如“今天投入了 83 分钟”，不使用空洞夸奖。
- AI 只建议；用户确认后才写入正式计划。

秘书禁止：

- 按逗号、句号或“然后”拆任务。
- 把“这是测试”“我梳理一下”等话语组织成分建成事项。
- 把粗粒度事项拆成联系客户、找素材、导出文件等细碎步骤。
- 在没有用户确认时修改正式计划。
- 把超容量事项悄悄加塞。
- 把逾期事项自动滚入第二天。
- 用固定模板或本地规则冒充 AI 判断。
- 把工作流误判成新项目，并在用户否决后反复询问。

## 4. 用户节奏和容量规则

- 工作日通常 09:00 起床、23:30 左右休息，最晚 01:00 真正休息。
- 休息日通常 10:00 起床，最晚 01:00 休息。
- 周六保持完整休息，不排工作承诺；生活安排可以出现。
- 周日 20:00–23:30 是默认大型周规划窗口，但错过后可在任何一天补做。
- 个人项目初始可靠容量：每周 7 小时。
- 主业显式专注任务容量：每周 20 小时，和个人项目分池计算。
- 连续使用四周后，依据真实计时和完成情况校准容量。
- 例外冲刺必须单独记录，不能提高未来常态容量。
- 每天最多确认 1–3 件工作重点。
- 普通事项只排到某一天，不维护小时级日历。

### 5.2 项目层级

统一使用：

> 项目组 → 核心项目 → 工作流/子项目 → 具体事项

示例：

```text
阿野IP
├─ 阿野在武汉
│  └─ 视频内容
│     └─ 剪辑3个阿野视频并设置引流钩子
└─ 是阿野吖
   └─ 公众号内容
      └─ 排版公众号文章

磕学家
└─ 同人内容生产
   └─ 梳理同人文创作流程

家庭财务
└─ 财务系统
   └─ 搭建家庭财务系统并整理数据
```

规则：

- 每个正式工作事项必须有一个主要核心项目。
- 工作流用于核心项目内部归类，不自动升级为新项目。
- 一件工作可以有“同时支持”的其他项目，但投入只能归入一个主要项目，不能重复计算。
- 新项目只有同时满足“独立长期结果 + 持续工作量”才允许建议建立。
- 新项目不会自动获得额外容量。
- 用户否决新项目后，必须保存长期归属记忆。
- 已确认规则：同人文创作、同人文流程、同人内容生产 → `磕学家 / 同人内容生产`，不是新项目。

## 6. 核心用户流程

### 6.1 周规划

```text
用户连续输入混乱原话
→ AI 每轮更新理解
→ 识别真实事项和核心项目
→ 只追问会改变排程的歧义
→ 用户说“就这些/开始排/帮我生成计划”
→ 检查估时、依赖、截止、容量和每天上限
→ 生成周一至周日建议
→ 明确保留、下周、取消/暂缓和受阻事项
→ 用户编辑并确认
→ 写入正式计划
```

没有固定“我说完了”按钮。用户通过自然语言结束收集。

### 6.2 周中新增

AI 必须读取：

- 当前正式承诺；
- 已投入时间；
- 剩余可靠容量；
- 本周剩余日期；
- 项目月度重点；
- 已确认依赖和外部条件。

如果新事项能加入，给出日期和理由；如果会挤掉旧事项，必须明确说“要插入它，建议顺延/取消哪一件”。

### 6.3 现实变化

输入“客户给素材了”“小李回复了”等内容时，AI 判断它是否解除外部条件，并找到因此可激活的事项。若激活会影响当前计划，仍需给出调整方案并等待确认。

### 6.4 逾期和旧数据

- 计划日期已过的未完成事项进入“逾期待决”。
- 缺少日期的旧事项进入“待重排”。
- 单日超过 3 件的旧事项只保留前三件，其余进入“待重排”。
- 明显测试句进入“旧版待清理”。
- 以上状态都不能自动进入今天或正式周报。
- 用户可以让秘书集中给出移动、下周、取消或受阻建议。

### 6.5 每日执行和计时

- 首页只展示当天确认的 1–3 件工作和单独的生活安排。
- 工作支持开始、暂停、继续和结束。
- 暂停只停表，不能退出专注页；继续后累计，不从零开始。
- 结束后询问“已完成 / 还没完成”。
- 未完成时填写预计剩余时间，不自动滚到明天。
- 关系类生活安排默认不计时，但作为现实约束参与排程。

### 6.6 复盘

每日 22:30 后打开 App 显示：

> 今天投入了 X；本周关键事项还差 Y；明天最值得先做的是 Z。

周报包含：

- 正式工作承诺的完成、未完成、受阻、预计和实际；
- 单独的生活安排；
- 总专注投入和估时偏差；
- 按核心项目和工作流分组的投入；
- 基于真实事实的 AI 判断；
- 明确的下周继续、顺延、取消、调估时或解除依赖建议。

## 7. AI 调用设计

当前关键代码均在 `app.js`。

### 7.1 原话理解层

- 入口：`understandSecretaryTurn()`。
- 提示词：`UNDERSTAND_SYSTEM`。
- 目标：理解整轮原话、更新完整候选列表、识别核心项目、工作流、依赖和关键问题。
- 输出：严格 JSON。
- 必须传入 `projectDecisions`，避免重复询问已否决的新项目。
- `finishIntent` 用于识别“开始排”等自然结束意图。

### 7.2 排程决策层

- 入口：`buildScheduleProposal()`。
- 提示词：`scheduleSystemPrompt(mode)`。
- 使用项目重点、关键路径、机会成本、收入验证、时效窗口、历史耗时和艾森豪威尔重要/紧急视角。
- 输出周计划、既有事项调整、完成方式建议、完成标准和容量结论。
- 本地 `rebalanceProposalItems()` 再做容量和每日 3 件上限兜底。

### 7.3 周报与月度复盘

- 周报入口：`generateWeeklyReport()`。
- 月度入口：`buildMonthlyProposal()`。
- 禁止固定鸡汤；必须引用真实任务、计时、项目投入和收入。

### 7.4 DeepSeek 配置

- 模型常量：`deepseek-v4-pro`。
- API：`https://api.deepseek.com/chat/completions`。
- 使用 JSON response format 和 thinking。
- Key 读取自 `state.settings.apiKey`。
- Key 不得进入公开周报、Git、错误日志或备份。

## 9. 当前已经实现

- 超容量时本地兜底把低优先级事项明确移到下周。

### 9.3 项目归属

- 核心项目和项目组种子数据。
- 工作流字段和项目路径展示。
- 正式工作确认前强制要求核心项目。

- “同人文创作”不会再次建议新建，自动映射到“磕学家 / 同人内容生产”。
- 月度项目页显示已出现的工作流。
- 周报按核心项目和工作流分组。

### 9.4 数据迁移与排程

- 旧任务不再自动滚入本周或今天。
- 逾期、缺日期、明显测试句和单日超限任务进入独立待处理状态。
- 家庭财务系统类旧生活记录迁移为“家庭财务 / 财务系统”待重排工作。
- 周六不排工作。
- 每天最多 3 件工作。
- 主业和个人项目使用独立容量池。

### 9.5 交互与复盘

- 删除候选事项时保持当前视口，不再整页平滑滚到底部。
- 工作和生活在周历中分区展示。
- 周报事项支持打开、编辑和删除。
- 容量负数显示“超载”，不再伪装成剩余 0 小时。
- JSON、Markdown 和 CSV 导出。
- 周报快照、项目投入和收入记录。

当前家庭网络使用手机热点和 Verge。浏览器系统代理为：

```text
127.0.0.1:7897
```

Git 不会自动读取 Windows 系统代理。如果普通 `git push` 连接 GitHub 443 超时，使用仅当前 PowerShell 进程生效的代理：

```powershell
$env:HTTP_PROXY='http://127.0.0.1:7897'
$env:HTTPS_PROXY='http://127.0.0.1:7897'
git push origin master
```

不要未经用户允许写入 Git 全局代理配置。

## 16. Claude Code 工作规则

1. 修改代码前先给方案，等待用户回复“开始、同意、可以、做吧”。
2. 不把用户尚未确认的建议写入正式计划。
3. 不为了视觉重构破坏 localStorage 兼容和已有数据。
4. 修改 schema 必须编写迁移，并保证真实事项不被静默删除。
5. 修改 AI JSON 结构时同时更新提示词、归一化、UI、确认写入和错误处理。
6. 修改 Service Worker 时同步更新缓存名、资源版本和注册版本。
7. 至少执行 `node --check app.js`、`node --check sw.js` 和对应真实浏览器回归。
8. 提交信息使用中文。
9. 工作流终点是 `add → commit → push`；当前推送到 `master`。
10. 不安装新依赖、不改变全局 Git/代理配置，除非用户明确同意。

---

接手判断标准：如果一个改动让用户更少计算、更少焦虑，同时仍能看见真实容量、项目归属和取舍代价，它大概率符合“未尽”的方向；如果只是增加更多字段、按钮和维护负担，应先重新审视。
